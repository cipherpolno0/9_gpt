## เริ่มจากหน้าที่ที่ทำอยู่

เข้าสู่บัญชีกลาง เลือกหน่วยงาน/หน้าที่/ช่วงมอบหมายที่ยังใช้ได้ ทุกคำสั่งตรวจ server ซ้ำ การเปลี่ยนช่องหน่วยงานใน browser ไม่เพิ่มสิทธิ์ หนึ่งบัญชีมีหลายหน้าที่ได้ แต่รายการของหน้าที่Aไม่ทำให้เปิดเอกสารหน้าที่Bได้ ถ้าพ้นหน้าที่Bแล้วรายการเก่าไม่ให้สิทธิ์อ่านโดยปริยาย แม้มีลิงก์ receipt หรือเคยเป็นผู้รับ

ถ้าจำเป็นต้องอ่านเรื่องเก่าด้วยภารกิจตรวจสอบใหม่ ให้ขออำนาจ/ACLเฉพาะ action/purpose/source/รุ่นไฟล์ตามนโยบาย ผ่านผู้ตรวจคนละคน ไม่กู้สิทธิ์เก่าด้วยชื่อฝ่ายหรือtechnicaladmin Receiptในอดีตไม่ถูกลบเมื่อสิทธิ์หมด แต่ผู้ตรวจย้อนหลังต้องมีสิทธิ์ปัจจุบัน ไม่มีคำสั่งรวมบัญชีหรือสร้างloginสารบรรณอีกชุด

## เจ้าหน้าที่ร่างและตรวจ

1. เลือกประเภทหนังสือรับ/ส่ง/ภายใน/เวียนจาก config ที่ยืนยัน แยก priority กับ confidentiality ไม่เลือก “ด่วน” เพื่อให้เห็นไฟล์ลับได้
2. เลือกเรื่องต้นทาง/หน่วยงาน/Person IDs ให้ชัด ผู้ชื่อซ้ำดูรหัสและสังกัด เลือก Document/FileVersion กลางที่ผ่านตรวจ ไม่อัปโหลดสำเนาเพื่อหลีกเลี่ยง ACL
3. กรอกหัวเรื่อง เนื้อหา ผู้ลงนาม ผู้รับ context วันกำหนด และเอกสารแนบ ตรวจทานสิ่งที่ผู้รับจะเห็น บันทึกร่าง/reloadแล้วใช้ revisionปัจจุบัน ถ้า conflict ให้โหลดและเทียบข้อมูล ไม่กดบันทึกทับเงียบ ๆ
4. ส่งตรวจ ผู้ตรวจส่งกลับพร้อมเหตุผลหรือเสนอผู้อนุมัติ ผู้สร้างแก้ revision ใหม่ในเรื่องเดิม ไม่สร้างเรื่องซ้ำเพื่อแก้รายการreturned ผู้สร้าง/ผู้ไม่มีอำนาจอนุมัติผ่าน API ไม่ได้
5. ผู้อนุมัติอ่านรุ่นเดียวกับ manifest/ไฟล์ที่จะตัดสิน ตรวจสิทธิ์ตามวันที่และmaker checker อนุมัติแล้วตรึงรุ่น การแก้สาระสำคัญต้องหยุด active dispatch permit และตรวจรุ่นใหม่ เก็บคำตัดสินเก่า
6. ออกเลขตาม policy ของประเภทและหน่วยงาน ปีทะเบียนเป็นคนละความหมายกับปีงบ/การศึกษา เลขVOIDต้องมีเหตุผลและหลักฐาน ไม่นำกลับใช้กับเรื่องอื่น รูปแบบเลขและขั้นตอนทางการยังTO VERIFY

ภายใต้สถานะ repository ปัจจุบัน ขั้นตอนข้างต้นยังทำผ่านหน้าเว็บไม่ได้ ไม่ใส่เลขจริงหรือใช้fixtureเป็นหนังสือทางการ

## ส่งหนังสือและตรวจผู้รับ

ก่อนส่งตรวจ Person/Organization/context ทุก endpoint และไฟล์ exactรุ่นที่อนุมัติ ถ้า directกับgroupซ้ำผู้รับหน้าที่เดียว ระบบควรรวมdeliveryหนึ่งรายการและเก็บที่มาทั้งคู่ คนเดียวสองหน้าที่แสดงแยก ไม่รับทราบแทนกัน Group snapshotยึดสมาชิก ณ วันส่ง เพิ่มสมาชิกภายหลังไม่ทำให้เห็นหนังสือเก่า ต้องใช้การส่ง/ขอสิทธิ์ใหม่ตาม policy ไม่แก้กลุ่มเก่าเงียบ ๆ

เมื่อยืนยันส่งได้รับเลขติดตามการส่ง ยังไม่แปลว่าส่งถึง ผู้ส่งดูผลรายผู้รับ ไม่กดส่ง intent ใหม่เพียงเพราะ workerล่าช้า ไม่เปิดเนื้อหาลับในnotification/อีเมล/ชื่อไฟล์ที่ผู้ไม่มีสิทธิ์เห็น และไม่ส่งอีเมลจริงหากช่องทาง/ผู้รับ/สิทธิ์ยังไม่ตั้งค่าที่รับรอง

## ผู้รับและผู้ถูกมอบหมาย

เปิด inbox ในหน้าที่ปัจจุบัน ตรวจเลขทะเบียน/รุ่น/contextและข้อมูลที่ได้รับสิทธิ์ เปิดแจ้งเตือนหรือ preview ไม่รับทราบโดยอัตโนมัติ กดยืนยันรับทราบรุ่นนี้ชัดเจนเมื่อทำได้ บันทึกเวลาserver/actor/context Retryไม่สร้างreceiptซ้ำ การรับทราบหน้าที่Aไม่ยืนยันแทนB

ผู้มอบหมายเลือกผู้รับงานตามPerson ID+Organization+context ถ้าสิทธิ์อ่านเรื่อง/source/file/classไม่ครบเป็น pending_access ไม่ให้ไฟล์ลับผ่านtask/notification/link ขอสิทธิ์ตามนโยบายและผู้อนุมัติคนละคนก่อนactivate ผู้รับงานตรวจสภาพ/ผลดำเนินการแนบหลักฐานแล้วส่งcompleted การทำงานหนึ่งงานเสร็จไม่ปิดงานพี่น้อง

ผู้มีอำนาจปิดเรื่องตรวจเงื่อนไขการรับทราบและงานค้างตามclosure policy กดยืนยันพร้อมเหตุผล/หลักฐาน เก็บhistory ไม่ลบเอกสาร/เลข/receipt/source transactions ไม่ยกเลิกholdหรือเผยแพร่จากการปิดเรื่อง ถ้ายังไม่ยืนยันpolicyให้ปิดofficialcloseและแสดงข้อค้าง ไม่ใช้การเปิดหน้าแทนคำสั่งปิด

## Retention การลงนาม และข้อยืนยัน

เมื่อครบอายุเก็บที่หน่วยงานยืนยันให้เสนอรายการตรวจ ไม่ลบอัตโนมัติ Holdครอบคลุมsource/file/derivativesตามscopeและยังไม่เพิ่มสิทธิ์อ่าน การปลดholdต้องอำนาจและคำตรวจเฉพาะไม่ใช้วันหมดอายุเอง Storagehold-vs-purge protocolของบท56ยังไม่ผ่านจึงปิดdestructiveexecution

หลักฐานอนุมัติภายในต้องมีจริงก่อนแสดงว่ามีภาพ/ปุ่ม/hashไม่ใช่certificate-basedsignature ตอนนี้ providerยังไม่ยืนยันและruntimeยังไม่มี ต้องแสดงSIGNING_NOT_CONFIGUREDเมื่อบริการพัฒนาจริง ไม่แสดงลงนามทางการสำเร็จจากfixture/internal evidence ถ้าต้องเชื่อมproviderใช้sandboxและเก็บผลตรวจจริงโดยprivatekeyอยู่นอกแอปตามบท57
